# 本机性能实验（2026-09-17）

环境：Windows，AMD Ryzen 7 9800X3D，LLVM-MinGW Clang 22.1.8（命令名 gcc），C11，无 -O 优化。源代码为本次简化版本，保留 PDF 要求的从 2p 开始筛选。

## 接近 2 秒／10 秒的结果

| 程序 | 预算 | 本次预算内最大已测 n | 对应最后质数 | 实测秒数 | 较大输入的结果 |
|---|---|---:|---:|---:|---|
| print-primes | 2 秒 | 5,500,000 | 5,499,979 | 1.844 | 6,000,000 用 2.079 秒 |
| print-primes | 10 秒 | 18,000,000 | 17,999,987 | 9.612 | 20,000,000 用 11.141 秒 |
| sieves-heap | 2 秒 | 87,500,000 | 87,499,967 | 1.823 | 100,000,000 用 2.094 秒 |
| sieves-heap | 10 秒 | 450,000,000 | 449,999,993 | 9.888 | 500,000,000 用 11.042 秒 |

| sieves | 10 秒 | 1,000,000 | 999,983 | 0.031 | 同上：增加时间不能增加栈容量 |

“最大已测”是这批样本中的最大成功输入，不是逐整数证明的绝对最大值。每次只测一次，接近时间边界的结果会随负载变化；10 秒的 heap 样本尤其接近阈值。stack 版先碰到内存限制，不能靠等待到两秒或十秒继续增大 n。其容量界限只定位在 1,000,000 与 1,025,000 之间，没有修改默认栈设置。

## 方法及解释

编译：

```text
gcc -std=c11 -Wall -Wextra -pedantic print-primes.c -o print-primes.exe
gcc -std=c11 -Wall -Wextra -pedantic sieves.c -o sieves.exe
gcc -std=c11 -Wall -Wextra -pedantic sieves-heap.c -o sieves-heap.exe
```

本机测试脚本用 Python subprocess.run 逐个启动可执行文件，stdout=subprocess.DEVNULL，time.perf_counter 记录完整进程的 wall-clock time（墙钟时间）。计时包括启动、分配、筛选、printf 格式化和写入空设备，不包含终端绘制，也不是纯计算时间。stdout 丢弃，不额外储存海量文本。

最后质数是在成功退出的对应 n 下，由独立 Python 试除法向下求得；不是从计时进程的输出文件中抄录。代码打印到 n 的行为另由 204 组输入的完整输出核对验证。失败运行没有“最后质数”记录。

对试除和 heap 版本，先扩大输入跨过目标时间，再做三次区间缩小；对 stack 版测试容量限制。没有增加 -O3、改变筛法或增加栈来提高数字。可复现的测试脚本及原始 JSON 保存在本地 lab2-work/revision-20260917/。

要在 Windows 单独复测一个数据点，可在 PowerShell 运行：

```powershell
Measure-Command { cmd /c ".\print-primes.exe 5500000 > NUL" }
Measure-Command { cmd /c ".\sieves-heap.exe 87500000 > NUL" }
```

这会额外计入 cmd 启动开销，故不要求与 Python 数字完全相同。KTH Linux 可以用 `time ./print-primes 5500000 > /dev/null`。直接在终端打印通常还受显示速度影响，答题时必须说明输出方式。

试除法重复测试各候选数的因数；筛法通过标记共享结果，所以两者规模差别大。stack/heap 的算法相同，主要差别是可用空间和内存分配方式。本机值不能当作 DTEK-V 的固定答案。
